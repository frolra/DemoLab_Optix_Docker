# Troubleshooting

- `install.sh` exits immediately with `ERROR: .env failed pre-flight validation (nothing was changed):` followed by a bulleted list: this is expected and intentional — every problem in `.env` is checked and reported together *before* anything is touched (no files written, no containers started), so fix every listed item in `.env` and re-run; a common cause is copying `.env.example` without replacing all `CHANGE_ME` placeholders, or `MSSQL_SA_PASSWORD` not meeting SQL Server's own complexity rule (8+ characters, at least 3 of lowercase/uppercase/digit/symbol).
- `bash\r`: run `dos2unix install.sh prepare-ldap.sh prepare-jwk.sh prepare-mqtt.sh`.
- Caddy restart loop: inspect `docker compose logs caddy` and validate the generated `Caddyfile`.
- `./install.sh` re-run against an already-installed deployment (for example, to add a new service like the CSR Generator) fails at step `[2/12]` with an error from `step ca provisioner add acme` such as `"provisioner with name acme already exists"`, and the whole script aborts: this was a bug in earlier v1.1 builds — `install.sh` always tried to add the ACME provisioner, whether or not it was already there, and step-ca's own admin API refuses to store a second provisioner with the same name (confirmed in step-ca's source, `authority/provisioners.go`). Fixed: `install.sh` now inspects the CA's own config for an existing `acme` provisioner first and skips the add step entirely if found, logging `ACME provisioner already present; skipping`. Re-running `./install.sh` on an existing deployment is now safe and is the supported way to add a new service — see [Adding a Web Application](ADDING_WEB_APP.md#adding-a-service-to-an-already-running-deployment) for exactly what does and doesn't happen on a re-run.
- `./install.sh` re-run against an already-installed deployment fails at step `[8/12]` with `ldap_sasl_bind(SIMPLE): Can't contact LDAP server (-1)`, and `docker compose logs openldap` (or `docker logs openldap`) shows a continuous flood of `TLS: can't accept: (unknown)` / `closed (TLS negotiation failure)` for every single new connection — including plain `ldapsearch` calls that worked fine moments earlier — meaning OpenLDAP's TLS listener itself has broken, not just this one script's connection attempt: this was a confirmed, real bug in earlier v1.1 builds, root-caused with the affected deployment's own live diagnostics (`ldapsearch` retried directly on the VM still failed identically, ruling out a transient issue) plus the `vegardit/openldap` image's own documentation. `install.sh` always unconditionally re-ran `prepare-ldap.sh` (regenerating `ldap/certs/ldap.crt`/`ldap.key` via `docker cp` from step-ca) and then re-applied the RootDN password via a live `cn=config` edit (`ldapmodify -Q -Y EXTERNAL`), even against an already-running, already-working OpenLDAP. `docker cp` writes container-to-host files owned by whoever ran the command (the installing user, not the container's internal `openldap` service user — this is documented Docker behavior, not a bug in Docker itself), and the `vegardit/openldap` image re-validates/reconciles its TLS certificate and key sources as part of reacting to that live `cn=config` change; with the freshly-`docker cp`'d files now owned by the host user instead of the container's `openldap` UID, that reconciliation fails and takes the TLS listener down for every subsequent connection, not just the one that triggered it. This is the same *class* of bug (host-user-owned secret files unreadable by a container's internal non-root service user after a privilege drop) already fixed twice before in this project for Mosquitto, but this time the correct fix is different: rather than trying to make `docker cp`'s ownership safe for OpenLDAP's live reconciliation, `install.sh` now detects "was LDAP already bootstrapped" by checking whether `ldap/certs/ldap.crt`/`ldap.key` already have content *before* anything is touched, and — if so — skips both the certificate regeneration (step `[6/12]`) and the entire RootDN/webadmin bootstrap (step `[8/12]`) entirely, logging an explanatory message instead of touching an already-working LDAP setup at all. If your deployment already hit this failure before pulling the fix (OpenLDAP's TLS listener is currently broken), pull the fix and run `docker compose restart openldap` to force a clean restart of the container using its already-committed configuration and the certificate/key files already on disk (the restart itself does not go through `install.sh`'s TLS reconciliation trigger, so it should come back up healthy); then re-run `./install.sh`, which will now correctly detect the existing LDAP certificate and skip re-touching it.
- StepCA Web's "Submit CSR" form (X.509 → Active Certificates) fails with `Failed to sign certificate` (no further detail in the browser) even though the CSR is valid: the real reason is only ever printed to the `stepca-web` container's own logs (`docker compose logs stepca-web`, look for a line starting with `❌ Error:`), never shown in the UI — check that first for any occurrence. Two confirmed causes so far: (1) `❌ Error: 403 - ... "certificate request does not contain the valid IP addresses - got [...], want []."` — a CSR with an IP SAN (e.g. `IP:127.0.0.1`) was rejected because `stepca-web` (a separate repository, `frolra/stepca-web`) only read `DNSName` values off the CSR's SAN extension when building the JWT's `sans` claim, silently dropping IP SANs; fixed upstream in `frolra/stepca-web` (`extract_sans_from_csr` now reads `IPAddress` values too) — pull it inside the deployment's `stepca-web/` directory and rebuild (`cd stepca-web && git pull && cd .. && docker compose up -d --build stepca-web`). (2) The issued certificate's subject only ever contains the Common Name, silently dropping Organization/Organizational Unit/Country/State/Locality even though they're correctly present in the submitted CSR (verify with `openssl x509 -in cert.pem -noout -subject`): this is step-ca's own *default* x509 template behavior, confirmed by reading step-ca's source (`x509util.DefaultLeafTemplate` sets `"subject": {{ toJson .Subject }}`, where `.Subject` is built by `CreateTemplateData(commonName, sans)` and only ever holds the Common Name — every other subject field is discarded regardless of what's in the CSR or in the request's `templateData`, since a per-request `templateData` is only ever consulted by step-ca when the *provisioner itself* has a custom x509 template configured, which this lab's auto-created `admin` JWK provisioner never did). Fixed: `install.sh` now configures a custom x509 template on the `admin` JWK provisioner (the one `stepca-web` signs through) that copies the CSR's real subject through via `.Insecure.CR.Subject` instead of the default `.Subject`; re-running `./install.sh` against an existing deployment applies this automatically (it's an idempotent, always-reapplied config value, unlike the ACME/LDAP steps above that must be skipped on a re-run).
- `https://<HOSTNAME_FQDN>` (the bare hostname, no subdomain) fails with `ERR_SSL_PROTOCOL_ERROR`, `http://<HOSTNAME_FQDN>` works fine, and StepCA Web's ACME Orders page shows the `dns: <HOSTNAME_FQDN>` order stuck in `pending` with no certificate ever issued (every other order, `stepca.<host>`, `portainer.<host>`, etc., shows `valid`): this was a bug in earlier v1.1 builds. step-ca validates ACME challenges by connecting to the identifier's hostname over the internal `web` Docker network, and Caddy's `web` network entry only declared aliases for each `<service>.<HOSTNAME_FQDN>` subdomain — never for the bare `<HOSTNAME_FQDN>` itself — so step-ca could never resolve/reach Caddy for that one identifier, and the challenge never completed. Fixed by adding `${HOSTNAME_FQDN}` itself to Caddy's network aliases in `docker-compose.yml`. After pulling this fix, `docker compose up -d` recreates the `caddy` container with the new alias; Caddy's automatic HTTPS retries pending orders on its own with backoff, so the certificate should go from `pending` to `valid` within a minute or two without any other action. If it doesn't, restart Caddy (`docker compose restart caddy`) to force an immediate retry.
- Browser trust error: expected on first visit to any `*.<HOSTNAME_FQDN>` site, including the Certificate Portal itself, until `root_ca.crt` is imported — see [Certificate Download Portal](CERTIFICATE_PORTAL.md#why-it-stays-on-https-and-the-warning-youll-see-on-first-visit) for why, and verify the fingerprint before importing.
- phpLDAPadmin 500: use the complete `webadmin` DN and inspect `/app/storage/logs` in the container.
- Missing or invalid `jwk_key.json`: re-run `./prepare-jwk.sh` (step-ca must already be up and healthy). It regenerates the file from the CA's own JWK provisioner using `STEPCA_PASSWORD`; it no longer needs to be manually restored.
- StepCA Web certificate signing fails with a provisioner or `kid` mismatch: confirm `settings.json`'s `ca.admin_provisioner_name` matches the provisioner name printed by `./prepare-jwk.sh` ("Using JWK provisioner: ..."); re-run `./install.sh` or `./prepare-jwk.sh` followed by re-running the `settings.json` update in `install.sh` if they have drifted apart.
- `install.sh` fails at "Staging the certificate download portal" with `ERROR: unresolved variable in scripts/add-hosts-entries.sh.template`: this was a bug in earlier v1.1 builds — the template legitimately contains other bash `${VAR}` syntax (`${HOSTS_FILE}`, `${TMP_FILE}`, `${HOSTNAMES[@]}`) meant to stay untouched as real runtime variables, but the generation step's validation rejected any leftover `${...}` at all instead of checking specifically for `${HOSTNAME_FQDN}`/`${HOST_IP}`. Fixed; just re-run `./install.sh`.
- Can't reach `https://certificates.<HOSTNAME_FQDN>` to download the hosts-file scripts because no hosts entry exists yet for that name: this is the exact bootstrap problem the scripts solve, so don't try to add that one entry manually first. Instead browse to `http://<HOST_IP>` (works immediately, no DNS/hosts entry needed, no certificate involved) — see [Certificate Download Portal](CERTIFICATE_PORTAL.md#bootstrapping-without-any-dnshosts-entry-first).
- Hosts-file script produced duplicate entries: this was a bug in earlier v1.1 builds where the script only removed its own previously-added block, so any hostname line added manually (for example while working around the bootstrap issue above) was left in place and duplicated on every run. Fixed — the scripts now strip any pre-existing line for their target hostnames before writing their block. Re-download and re-run the script once to clean up existing duplicates; you can also just delete the extra lines by hand in the hosts file.
- Mosquitto fails to start or MQTTS handshake fails: confirm `mosquitto/certs/server.crt`, `server.key`, and `ca.crt` exist and are non-empty; re-run `./prepare-mqtt.sh`.
- Mosquitto restart-loops with `Error: Duplicate password_file value in configuration` (and similar for `allow_anonymous`): this was a bug in earlier v1.1 builds — `mosquitto.conf` repeated `password_file`/`allow_anonymous` after each `listener` block, but Mosquitto's `per_listener_settings` defaults to `false`, meaning those options are global, not per-listener; declaring the same global option twice is a fatal config error. Fixed by declaring them once, before the listener blocks. `docker compose up -d --build` (or a full `./install.sh` re-run) picks up the corrected file.
- Mosquitto logs a wall of `chown: /mosquitto/...: Read-only file system` lines on every start: harmless. The `eclipse-mosquitto` image's own entrypoint always tries to `chown -R /mosquitto` before starting, but our config/certs/secrets are intentionally bind-mounted read-only; the broker still runs as root regardless and can read them fine. Not something to fix — read-only mounts are the more secure choice here.
- Mosquitto restart-loops with `Error: Unable to open pwfile "/mosquitto/secrets/mosquitto.passwd"` (even right after a clean `./install.sh` from scratch, with the file present and looking normal on the host): the real, confirmed root cause is a permission requirement, not a mount or ownership bug. Mosquitto's own source (`src/mosquitto.c`) drops root privileges to its internal `mosquitto` user (UID/GID `1883` in this image, see its Dockerfile) **immediately after parsing its config file — before opening any certificate or the password file**. Every file `prepare-mqtt.sh` generates is owned by the host user who ran it, so unless that user happens to have UID 1883, Mosquitto's own process can never read its private key or password file at all, no matter how the file got there. Fixed by having `prepare-mqtt.sh` `chgrp` `mosquitto/certs/server.key` and `mosquitto/secrets/mosquitto.passwd` to the `mosquitto` group (via a container that bind-mounts only that single file, never a whole directory) and `chmod 640` them, so the group-read bit lets Mosquitto's own user read them while the host user keeps ownership. `root_ca.crt`/`ca.crt`/`server.crt` need no change since they're already world-readable (644). Just re-run `./prepare-mqtt.sh`.
- Mosquitto fails with `Error: Unable to open pwfile "/mosquitto/secrets/mosquitto.passwd"` and `ls -la mosquitto/secrets` shows the directory (and/or file) owned by an unexpected numeric UID/GID like `1883:1883` instead of your own user: this was a *different*, earlier bug (now fixed) where `prepare-mqtt.sh` bind-mounted the entire `mosquitto/secrets` directory read-write to run `mosquitto_passwd`, and `eclipse-mosquitto`'s own entrypoint's unconditional `chown -R mosquitto:mosquitto /mosquitto` (whenever it starts as root) silently propagated back and reassigned ownership of the *host* directory. `prepare-mqtt.sh` self-heals this: if it detects `mosquitto/secrets` isn't owned by the current user, it removes it with `sudo` before recreating it (you'll be prompted for your `sudo` password). This is separate from, and was masking, the permission issue described above — a from-scratch install won't hit this one at all, only a checkout still carrying the corrupted directory from an old run.
- `prepare-mqtt.sh` fails with `chmod: cannot access 'mosquitto/secrets/mosquitto.passwd': Permission denied`: an even earlier bug, superseded by both fixes above (the file is no longer generated against a bind-mounted host path at all). Just re-run `./prepare-mqtt.sh`.
- MQTT client authentication fails: confirm `MQTT_USERNAME` / `MQTT_PASSWORD` in `.env` match what was used to generate `mosquitto/secrets/mosquitto.passwd`; re-run `./prepare-mqtt.sh` after changing either value.
- MQTTX Web cannot reach the broker over WSS: check `docker compose logs caddy` for the `mqttws.<HOSTNAME_FQDN>` block and confirm Mosquitto's `9001` listener is healthy with `docker compose logs mosquitto`.
- CloudBeaver cannot reach a database: confirm the target service is on the `database` network and that CloudBeaver's connection host matches the Compose service name (`postgres`, `mysql`, or `mssql`), not `localhost`.
- CloudBeaver still shows the "Configure Server" setup wizard on first visit even though `CLOUDBEAVER_ADMIN_USER` / `CLOUDBEAVER_ADMIN_PASSWORD` are set correctly in `.env`, and `docker compose logs cloudbeaver` shows `ERROR io.cloudbeaver.server.CBApplication - Error loading server auto configuration` followed by `User or team 'admin' already exists`: this was a confirmed, real bug in earlier v1.1 builds, root-caused by reading CloudBeaver's own server source (`CBDatabase`, `CBEmbeddedSecurityController`) since no local Docker was available to test-run it directly. Two compounding issues: (1) `cloudbeaver/initial-data.conf` used to set `adminName: "${CLOUDBEAVER_ADMIN_USER}"`, but that file has **no** `${VAR}` substitution (unlike `cloudbeaver.conf`) — the literal, unresolved string became a broken admin username; (2) more importantly, that file's `Administrators` team used `subjectId: "admin"`, and CloudBeaver treats user IDs and team IDs as one shared, lowercased namespace — so when the real auto-configuration mechanism (`CB_ADMIN_NAME`/`CB_ADMIN_PASSWORD`, set on the `cloudbeaver` service in `docker-compose.yml`) tried to create an admin *user* named `admin`, it collided with the *team* already named `admin`, threw the exception above, aborted the whole auto-configuration, and left the server stuck in "configuration mode" (wizard shown) forever. Fixed by removing `adminName`/`adminPassword` from `initial-data.conf` entirely (that file now only pre-seeds teams/permissions) and renaming the team's `subjectId` to `administrators` (the `user` team's `subjectId` must stay `user` — it has to match CloudBeaver's own `defaultUserTeam` default or the server refuses to start). If you still see the wizard after pulling this fix, the `cloudbeaver_data` volume likely already has a workspace from an older install (CloudBeaver only applies first-start configuration once); remove that volume for a full reset.
- SQL Server `sqlcmd` connection errors in the healthcheck: SQL Server can take a minute to accept connections on first start; wait for `docker compose ps` to report `healthy` before connecting.
