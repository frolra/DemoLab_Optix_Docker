# Security

- Never commit `.env`, generated certificates, LDAP secrets, MQTT secrets/certificates, `jwk_key.json`, or temporary password files.
- `jwk_key.json` contains private JWK material and is required by StepCA Web. As of v1.1 it is no longer a static file: `install.sh` generates it on every install by extracting and decrypting step-ca's own JWK admin provisioner key (via `prepare-jwk.sh`), so no fixed private key is shipped in the repository. The generated file is still sensitive; it is `chmod 600` and listed in `.gitignore`.
- Portainer's admin account is pre-provisioned from `PORTAINER_ADMIN_PASSWORD` via a single-use secret file (`portainer/secrets/admin_password`, `chmod 600`, generated by `install.sh` and listed in `.gitignore`), the same pattern used for `ldap/secrets/ldap-admin-password` and Mosquitto's password file. Never commit that file, and rotate `PORTAINER_ADMIN_PASSWORD` like any other lab secret if it may have been exposed.
- **Historical exposure (remediated):** the repository's history before this release contained a static, committed `jwk_key.json` with real private key material, and `.env.example` carried real (non-`CHANGE_ME`) test credentials across several commits. That history has been discarded and this repository restarted from a single clean commit with no trace of either. If you (or anyone) still has a clone, fork, or local checkout of the old history, treat the JWK key and the test credentials that were in `.env.example` (`STEPCA_PASSWORD`, `POSTGRES_PASSWORD`, `LDAP_ADMIN_PASSWORD`, `KEYCLOAK_ADMIN_PASSWORD`, `INFLUXDB_ADMIN_PASSWORD`, `STEPCA_WEB_SECRET_KEY`, `PHPLDAPADMIN_APP_KEY`) as compromised: rotate them, and recreate the corresponding JWK provisioner on any CA that used that key.
- Do not reuse lab credentials in production.
- Restrict ports 389, 636, and 9000 as appropriate.
- v1.1 exposes PostgreSQL (5432), MySQL (3306), SQL Server (1433), and Mosquitto MQTTS (8883) directly to the network. Set the corresponding `*_BIND_IP` variables in `.env` to a specific interface instead of leaving them on all interfaces if the host is reachable from an untrusted network.
- **Mosquitto's plain MQTT listener (1883) is unencrypted and fully anonymous by design** — no certificate, username, or password of any kind is required to publish/subscribe to any topic. This is an intentional lab convenience (see [docs/MQTT.md](MQTT.md)), not a safe default outside a controlled network: anyone who can reach `MQTT_BIND_IP:1883` has full read/write access to the broker. Set `MQTT_BIND_IP` to a specific, trusted interface, and consider disabling this listener entirely (remove the `1883` block from `mosquitto/config/mosquitto.conf` and the corresponding port mapping in `docker-compose.yml`) once it's no longer needed for testing.
- The `database` network keeps MySQL, SQL Server, PostgreSQL, and CloudBeaver isolated from Caddy and every other web-facing service; Caddy never joins `database`, and only CloudBeaver bridges `web` and `database`.
- The Certificate Download Portal (`cert-portal`) is mounted read-only from `certs-portal/public/`, a directory that `install.sh` populates with only public certificates and a fingerprint manifest. Never mount `/home/step/secrets`, the full `step` volume, or `jwk_key.json` into the portal, and never copy `root_ca_key`, `intermediate_ca_key`, or `mosquitto/certs/server.key` into `certs-portal/public/`.
- Rotate `MQTT_PASSWORD`, `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `MSSQL_SA_PASSWORD`, `CLOUDBEAVER_ADMIN_PASSWORD`, and `PORTAINER_ADMIN_PASSWORD` the same way other lab secrets are rotated; none are printed by `install.sh`.
- `cloudbeaver/initial-data.conf` contains `${CLOUDBEAVER_ADMIN_USER}` / `${CLOUDBEAVER_ADMIN_PASSWORD}` placeholders resolved by CloudBeaver itself from the container environment, not literal credentials; the file itself is safe to commit, but the resolved account still uses a real secret from `.env`.
